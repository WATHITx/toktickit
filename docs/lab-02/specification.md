# Lab 2 Sprint Engineering Specification

> Draft — review every line, adjust to match your actual implementation decisions,
> then commit to `docs/lab-02/specification.md` before starting implementation PRs.

## 1. Sprint Goal

Deliver a Requester-facing TokTickIT ticketing experience that lets a selected
Development Requester create a support ticket, view and search their own tickets,
inspect ticket details, and manage supporting attachments — all backed by real
PostgreSQL data through the REST API built in Lab 1, with a consistent Zen Green
UI foundation that later labs will reuse.

## 2. Stakeholder Request Interpretation

The IT department wants Requesters to submit real support tickets: describing a
problem, classifying it by category and related system, setting a requested
priority, and attaching evidence. Because full authentication is not yet built,
the system needs a temporary "Development Requester" selector that simulates a
logged-in user for testing multi-user ownership. Requesters must only ever see
and manage their own tickets and attachments.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism, not real auth)
- Create Ticket screen, validation, and ticket creation API
- My Tickets screen: search, filter, sort, pagination
- Requester Ticket Detail screen (read-only ticket header)
- Attachment lifecycle: upload, list, download, soft-remove
- Ownership enforcement (Requester A cannot access Requester B's data)
- Zen Green UI foundation and reusable component conventions
- Responsive layout at desktop / tablet / mobile breakpoints

### Excluded
- Authentication: login, logout, passwords, sessions, tokens, real authorization
- IT Staff dashboard, ticket assignment, IT Priority, status changes
- Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle beyond initial `NEW` status (resolve, close, reopen, cancel)
- Administrator functions (user/reference-data management)

## 4. Functional Requirements

- FR-01: The system shall allow selecting one active Development Requester as
  the current testing identity before any ticket screen is accessible.
- FR-02: The system shall allow the current Requester to create a new ticket
  with category, related system, summary, description, requested priority,
  and optional attachments.
- FR-03: The system shall generate a unique, backend-generated Ticket Number
  upon successful ticket creation.
- FR-04: The system shall list only the tickets owned by the current Requester
  in the My Tickets screen.
- FR-05: The system shall allow searching My Tickets by ticket number or
  summary text.
- FR-06: The system shall allow filtering My Tickets by category, requested
  priority, and current status.
- FR-07: The system shall allow sorting My Tickets by created date, ticket
  number, and current status.
- FR-08: The system shall paginate My Tickets results.
- FR-09: The system shall allow the current Requester to open a Ticket Detail
  screen only for tickets they own.
- FR-10: The system shall allow adding a permitted attachment (JPG, JPEG, PNG,
  WEBP, PDF; ≤5MB; ≤5 active per ticket) to an owned ticket.
- FR-11: The system shall allow downloading an active (non-removed)
  attachment belonging to an owned ticket.
- FR-12: The system shall allow soft-removing an owned attachment with a
  required removal reason; removed attachments remain visible as metadata but
  cannot be downloaded or previewed.
- FR-13: The system shall reject any request for ticket or attachment data
  that does not belong to the currently selected Requester.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend, must be
  unique, and follows the format `TKT-<year>-<6-digit sequence>` (e.g.
  `TKT-2026-000042`). The sequence is generated atomically using a dedicated
  PostgreSQL sequence inside the same database transaction that inserts the
  Ticket row, so concurrent submissions can never receive the same number
  (see Section 11 for why this replaces a simple row-count approach).
- BR-02: A new Ticket begins with Current Status `New`.
- BR-2A: The Create Ticket Submit button is disabled immediately on click and
  re-enabled only after the request resolves (success or error), preventing
  duplicate submissions from repeated clicks on the same form instance.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The
  selected identity is for testing only and is not authentication.
- BR-04: Only active Development Requesters appear in the selector; inactive
  Requesters are excluded.
- BR-05: A Requester may only view, list, or modify tickets and attachments
  they own; ownership is enforced on the backend, not only hidden in the UI.
- BR-06: Ticket Summary is required, trimmed, and limited to 150 characters.
- BR-07: Ticket Description is required, trimmed, and limited to 2000
  characters.
- BR-08: Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`.
- BR-09: Category and Related System must reference existing, active
  reference-data records.
- BR-10: Search, filter, and sort parameters that are invalid or unrecognized
  fall back to safe defaults rather than causing a server error.
- BR-11: If ticket creation fails after validation passes (e.g., a database
  error), no partial ticket record is retained, and the submitted form values
  are preserved in the UI for retry.
- BR-12: An attachment may only be added to a ticket owned by the current
  Requester, up to a maximum of 5 active (non-removed) attachments per ticket.
- BR-13: Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF; maximum
  file size is 5MB; violating uploads are rejected with a specific error
  message before any file is stored.
- BR-14: Removing an attachment is a soft removal: the record and its
  metadata remain in the database, marked `isRemoved = true` with a required
  removal reason and timestamp; it is excluded from download and preview.
- BR-15: If ticket creation succeeds but a subsequent attachment upload fails,
  the ticket remains created and valid; the failure is reported only for the
  attachment step, and the Requester may retry the upload afterward.
- BR-16: An empty My Tickets list (Requester owns zero tickets) displays a
  distinct empty state from a "no results for this search/filter" state.
- BR-17: The Development Requester Selection screen and Change Requester
  action will be replaced by real authentication in Lab 3; no business logic
  in this sprint may assume the selected identity is cryptographically
  verified.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for full detail. Summary:
- Application shell: TokTickIT title, My Tickets / Create Ticket navigation,
  current Requester display with Change Requester action, active-page
  indication, responsive mobile navigation (collapsible on small screens).
- Development Requester Selection: dropdown of active Requesters, loading /
  empty / error states, Continue action, explanatory "testing only" text.
- Create Ticket: grouped fields (system-generated vs. editable), Summary and
  Description given ample width, Attachments below main fields, primary
  Submit action with busy state, validation messages beside each field.
- My Tickets: search box, category/priority/status filters, sortable columns,
  pagination, Create Ticket shortcut, priority/status badges, empty and
  no-results states, responsive table→card transition on mobile.
- Ticket Detail: read-only ticket header fields visually distinct from
  Attachment actions; attachment list with active/removed states, upload and
  soft-remove controls with confirmation.
- Zen Green Theme tokens (colors, editable/read-only field styling, error,
  warning, success states) as defined in the Lab 2 handout Section 7.

## 7. Data Changes

New Prisma models added in this sprint:
- `RequesterUser` (id, name, email unique, isActive, createdAt)
- `Category` (reused from Lab 1: id, name unique, createdAt)
- `RelatedSystem` (id, name unique, isActive, createdAt)
- `Ticket` (id, ticketNumber unique, requesterId FK, categoryId FK,
  relatedSystemId FK, summary, description, requestedPriority enum,
  currentStatus enum default `NEW`, createdAt, updatedAt)
- `Attachment` (id, ticketId FK, fileName, storedName, fileType, fileSize,
  isRemoved default false, removedReason nullable, removedAt nullable,
  createdAt)

Indexes: `Ticket.requesterId`, `Ticket.currentStatus`, `Attachment.ticketId`
for common filter/lookup patterns. `RequesterUser.email` and
`Category.name`/`RelatedSystem.name` are unique for seed idempotency.

Migration: one migration per model group, applied via
`npx prisma migrate dev`, tracked in `server/prisma/migrations/`.

## 8. API Contract

See `docs/lab-02/api-spec.md` for full detail. Endpoints added this sprint:
- `GET /api/requesters` — active Development Requesters
- `GET /api/related-systems` — active Related Systems
- `POST /api/tickets` — create a ticket
- `GET /api/tickets` — paginated, searchable, filterable, sortable list
  scoped to a Requester
- `GET /api/tickets/:id` — one owned ticket with attachments
- `POST /api/tickets/:id/attachments` — upload an attachment
- `GET /api/attachments/:id/download` — download an active attachment
- `DELETE /api/attachments/:id` — soft-remove an attachment

## 9. Acceptance Criteria

- AC-01: Given valid Ticket data, when the Requester submits the form, then
  one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts
  to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A
  is requested, then the Ticket data is not returned.
- AC-04: Given the Summary field is empty, when the Requester submits the
  form, then a field-level validation message is shown and no API call is
  made.
- AC-05: Given the backend is unreachable, when the Requester submits a valid
  form, then a safe error message is shown and the entered values remain in
  the form.
- AC-06: Given a Requester has zero tickets, when My Tickets is opened, then
  an empty-state message distinct from "no results" is shown.
- AC-07: Given a search term that matches no tickets, when My Tickets is
  queried, then a no-results state is shown.
- AC-08: Given a ticket already has 5 active attachments, when a 6th
  attachment upload is attempted, then it is rejected with a clear message.
- AC-09: Given an attachment has been soft-removed, when a download is
  attempted, then the download is rejected and the file is not served.
- AC-10: Given an unsupported file type is selected for upload, when the
  Requester attempts to submit it, then the upload is rejected before any
  file is stored, with a specific error message.
- AC-11: Given the Development Requester dropdown is loading, when the
  Selection screen is opened, then a loading indicator is shown before data
  arrives.
- AC-12: Given only an inactive Requester exists, when the Selection screen
  loads, then that Requester does not appear in the dropdown.
- AC-13: Given the viewport is mobile width (<768px), when Create Ticket is
  opened, then fields stack vertically with no horizontal page scrolling.
- AC-14: Given the Requester clicks Submit on a valid form, when the request
  is still in flight, then the Submit button is disabled and a second click
  does not trigger a second ticket creation request.

## 11. Assumptions and Decisions

- **Ticket Number generation (BR-01):** a naive `SELECT COUNT(*)` followed by
  `INSERT` has a race condition — two simultaneous requests can read the same
  count and generate the same number, then one insert fails on the unique
  constraint with an unhandled 500 error. Decision: create a PostgreSQL
  sequence (`ticket_number_seq`) via a Prisma migration, and read
  `nextval('ticket_number_seq')` inside the same transaction as the Ticket
  insert. This is atomic at the database level regardless of concurrent
  requests, so it is safe from day one and needs no later rework.
- **Summary length (BR-06, 150 chars):** matches the length of a typical
  email subject line / list-view column width, keeps My Tickets table rows
  scannable, and is generous enough for a one-sentence problem statement.
- **Description length (BR-07, 2000 chars):** roughly 300–350 words — enough
  for a detailed problem report while bounding request payload size and
  preventing unbounded storage growth or trivial denial-of-service via huge
  text bodies.
- **Duplicate-submission prevention (BR-2A):** rather than server-side
  idempotency-key tracking (extra complexity not required by the handout),
  the Submit button is disabled for the duration of the request. This is
  sufficient because Lab 2 has no authentication/session layer to build a
  more robust idempotency key against; the limitation is noted for revisit
  when real sessions exist in Lab 3.
- **Attachment storage filenames:** the stored filename on disk is a
  server-generated UUID (`crypto.randomUUID()`), never the user-supplied
  original filename. This avoids path-traversal and filename-collision
  errors entirely; the original filename is kept only as display metadata
  (`fileName` column), never used to construct a filesystem path.
- **Attachment upload failure after ticket creation (BR-15):** ticket
  creation and attachment upload are two separate requests/transactions, not
  one combined transaction. If ticket creation succeeds and an attachment
  upload later fails, the ticket is not rolled back — this matches the
  handout's requirement that "the ticket remains created and valid" and
  avoids the far more error-prone approach of trying to roll back a
  successful ticket insert because of an unrelated file-upload failure.
- **Query parameter validation (BR-10):** all list-endpoint query parameters
  are validated with an allow-list (`sortBy` must be one of three known
  columns, `sortDir` must be `asc`/`desc`) and silently fall back to the
  default on anything else, rather than returning a 400. This keeps the My
  Tickets screen resilient to a stray or malformed URL without ever
  surfacing an error state for something as low-stakes as a bad sort param.
- **The Development Requester's identity** is passed by the frontend on each
  request (e.g., as a query/body parameter) rather than a secure session,
  consistent with BR-17; this will be replaced by real auth in Lab 3. Every
  endpoint that reads or writes Ticket/Attachment data re-validates ownership
  server-side on every request (never trusts a cached "current requester" on
  the frontend alone) so this limitation cannot be used to view another
  Requester's data even in Lab 2's dev-only trust model.
- **File storage** uses local disk (`uploads/`, excluded via `.gitignore`)
  rather than cloud storage, since cloud deployment is out of scope until
  later labs.
